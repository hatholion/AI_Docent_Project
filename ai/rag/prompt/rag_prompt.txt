현재 프로젝트에 박물관/유물 정보를 기반으로 하는 RAG 시스템을 구축하려고 한다.

중요한 점은 Silver 데이터를 바로 LangChain Document로 변환하지 않는 것이다.

먼저 현재 존재하는 3개의 Silver JSONL을 이용해서
이번 RAG 서비스에서 실제로 사용할 최종 구조화 데이터인 Gold 데이터셋을 생성하고,
그 Gold 데이터셋만을 기준으로 이후 RAG 파이프라인을 진행한다.

전체 파이프라인은 반드시 다음 구조를 따른다.

Silver JSONL 3개
    ↓
var_list.md 기반 필요한 변수 선택
    ↓
동일 유물 기준 join / aggregation
    ↓
Gold dataset 생성
    ↓
LangChain Document
    ↓
Chunking
    ↓
Embedding
    ↓
Chroma Vector DB
    ↓
Retriever
    ↓
Retrieval Evaluation
    ↓
Ollama LLM
    ↓
최종 RAG 답변


==================================================
0. 구현 전에 먼저 실제 데이터 조사
==================================================

현재 데이터는 다음과 같다.

data/
├── Silver_0923.jsonl
├── Silver_images_0923.jsonl
├── Silver_relations_0923.jsonl
└── var_list.md

코드를 바로 수정하지 말고 먼저 다음을 조사한다.

1. 현재 repository 구조
2. var_list.md 전체 내용
3. Silver_0923.jsonl schema
4. Silver_images_0923.jsonl schema
5. Silver_relations_0923.jsonl schema
6. var_list.md에 적힌 각 변수가 어느 Silver 파일에 존재하는지
7. 세 Silver 파일을 동일 유물 기준으로 연결할 수 있는 key
8. 각 파일에서 동일 유물에 여러 record가 존재하는지
9. image/relation 데이터가 1:N 관계인지
10. null / empty / duplicate 데이터 구조
11. 현재 프로젝트에 존재하는 RAG/Ollama/FastAPI 관련 코드

field 이름이나 join key를 추측하지 말고
반드시 실제 데이터를 확인한 후 결정한다.

구현 전에 다음 내용을 먼저 나에게 요약해서 보여준다.

- var_list.md 변수 목록
- 변수별 source Silver 파일
- join key
- Silver 파일 간 관계
- Gold dataset의 예상 schema
- 이후 구현할 파일 구조


==================================================
1. Silver와 Gold의 역할을 명확히 분리
==================================================

이 프로젝트에서는 다음과 같이 정의한다.

Silver:
정제되어 있지만 여러 용도로 사용할 수 있는 범용 데이터

Gold:
이번 RAG에서 실제로 사용할 변수만 선택하고,
세 Silver 파일을 동일 유물 기준으로 통합한 최종 구조화 데이터

중요:

Gold dataset은 LangChain Document가 아니다.

Gold dataset은 여전히 JSON 형태의 구조화 데이터이고,
Document 생성은 Gold 이후 단계에서 수행한다.

즉:

Silver
→ Gold
→ Document

순서를 반드시 유지한다.


==================================================
2. Gold dataset 생성
==================================================

var_list.md를 source of truth로 사용해서 Gold dataset을 생성한다.

세 Silver 파일에서 var_list.md에 명시된 필요한 field를 찾고,
동일 유물 기준으로 join한다.

다음 세 파일을 사용한다.

data/Silver_0923.jsonl
data/Silver_images_0923.jsonl
data/Silver_relations_0923.jsonl

동일 유물에 여러 image 또는 relation record가 있다면
정보를 버리지 말고 list 형태 또는 적절한 구조로 aggregation한다.

예를 들어 실제 데이터가 다음 구조라고 가정하는 것이 아니라,
실제 schema를 확인해서 이와 유사한 Gold record를 구성한다.

{
    "artifact_id": "...",
    "name": "...",
    "period": "...",
    "description": "...",
    "images": [...],
    "relations": [...]
}

위 field 이름은 예시이며 실제 데이터를 기준으로 정한다.

Gold에는 기본적으로 var_list.md에서 요구하는 데이터만 포함한다.

단 다음 정보는 데이터 추적을 위해 추가할 수 있다.

- artifact identifier
- 데이터 source
- 필요하다면 join/trace에 필요한 key

RAG에 사용하지 않는 Silver 원본 field를 무분별하게 Gold에 넣지 않는다.


==================================================
3. Gold dataset 저장
==================================================

생성한 Gold dataset은 별도 파일로 저장한다.

권장 위치:

data/gold/
└── Gold_0923.jsonl

또는 현재 repository 구조에 더 자연스러운 위치가 있다면
그 구조를 사용해도 된다.

단 Silver 원본 파일을 절대 수정하지 않는다.

Gold도 JSONL 형식을 사용해서

한 줄 = 한 artifact

구조로 저장한다.


==================================================
4. Gold dataset 생성 스크립트
==================================================

Gold 생성은 RAG indexing 코드와 분리한다.

가능하면 다음과 같은 스크립트를 만든다.

ai/rag/scripts/build_gold_dataset.py

실행 예:

uv run python ai/rag/scripts/build_gold_dataset.py

필요하다면:

--output
--overwrite

같은 옵션을 제공한다.

이미 Gold 파일이 존재하는 경우
사용자 의도 없이 자동 덮어쓰기하지 않는다.

예:

uv run python ai/rag/scripts/build_gold_dataset.py --overwrite


==================================================
5. Gold dataset 검증
==================================================

Gold 생성 후 반드시 다음을 검증한다.

1. 총 artifact 수
2. artifact identifier 중복 여부
3. identifier가 없는 record 존재 여부
4. var_list.md에서 요구한 field가 정상적으로 들어갔는지
5. Silver의 1:N relation/image 데이터가 정상 aggregation되었는지
6. null / empty 값 비율
7. Gold sample 3~5개 출력

가능하면 다음과 같은 간단한 summary를 출력한다.

Gold records: XXXX
Unique artifacts: XXXX
Duplicate artifact IDs: X
Missing artifact IDs: X

그리고 각 주요 field별 non-empty 개수도 확인한다.


==================================================
6. RAG는 Gold dataset만 사용
==================================================

Gold 생성 이후의 RAG 코드는
Silver JSONL을 직접 읽지 않는다.

반드시:

data/gold/Gold_0923.jsonl

을 읽어서 진행한다.

즉 RAG pipeline은 다음부터 시작한다.

Gold
→ Document
→ Chunk
→ Embedding
→ Vector DB

이렇게 분리함으로써
Silver → Gold 데이터 가공 로직과
RAG 실험 로직을 분리한다.


==================================================
7. Gold dataset을 실험마다 다시 만들지 않음
==================================================

Chunk size,
overlap,
chunking strategy,
embedding model,
retriever 설정을 바꾸는 실험에서는

동일한 Gold dataset을 사용한다.

예를 들어:

Experiment 1:
Gold_0923.jsonl
→ recursive 500
→ BGE-M3

Experiment 2:
Gold_0923.jsonl
→ recursive 800
→ BGE-M3

Experiment 3:
Gold_0923.jsonl
→ field_based
→ BGE-M3

Experiment 4:
Gold_0923.jsonl
→ recursive 800
→ multilingual-e5-large

처럼 사용한다.

실험마다 Silver에서 Gold를 다시 생성하지 않는다.

Gold의 내용 자체를 변경하는 것은
별도의 데이터 전처리 실험으로 취급한다.

이를 통해 chunking / embedding 실험에서
입력 데이터가 항상 동일하도록 보장한다.


==================================================
8. YAML config 구조
==================================================

실험에 사용할 설정은 YAML로 관리한다.

권장 구조:

ai/llm/configs/
├── base.yaml
└── experiments/
    ├── exp01_recursive_500.yaml
    ├── exp02_recursive_800.yaml
    ├── exp03_no_chunk.yaml
    └── exp04_field_based.yaml


base.yaml에는 Gold dataset 경로를 명시한다.

예:

data:
  gold_file: "data/gold/Gold_0923.jsonl"

chunking:
  strategy: "recursive"
  chunk_size: 800
  chunk_overlap: 120

embedding:
  model_name: "BAAI/bge-m3"
  device: "auto"
  normalize_embeddings: true
  query_prefix: ""
  document_prefix: ""

vectorstore:
  type: "chroma"
  base_dir: "ai/rag/storage/experiments"
  collection_name: "silver_artifacts"

retriever:
  search_type: "similarity"
  k: 5
  fetch_k: 20
  lambda_mult: 0.5

evaluation:
  dataset: "ai/llm/evaluation/evalset/eval_dataset_exp01.json"
  metrics:
    - recall_at_1
    - recall_at_3
    - recall_at_5
    - mrr

llm:
  enabled: false
  provider: "ollama"
  model: "qwen3:8b"
  temperature: 0.0


collection_name이 현재 Gold 기반이라는 의미가 더 적절하다면
예를 들어 다음처럼 변경해도 된다.

collection_name: "gold_artifacts"

실제 구현에서 일관되게 사용한다.


==================================================
9. YAML과 Gold 생성 설정 구분
==================================================

실험 YAML은 기본적으로

- chunking
- embedding
- vector store
- retriever
- evaluation
- llm

설정만 변경한다.

Silver → Gold 변환 규칙은 일반 RAG experiment YAML에서
매번 변경하지 않는다.

Gold 생성에 필요한 설정이 있다면
별도의 설정 영역 또는 별도의 YAML로 관리해도 된다.

예:

ai/llm/configs/gold.yaml

silver:
  artifact_file: "data/Silver_0923.jsonl"
  image_file: "data/Silver_images_0923.jsonl"
  relation_file: "data/Silver_relations_0923.jsonl"
  variable_file: "data/var_list.md"

gold:
  output_file: "data/gold/Gold_0923.jsonl"

단 프로젝트가 불필요하게 복잡해진다면
Gold 관련 경로는 build_gold_dataset.py 또는 base config에서 관리해도 된다.

핵심은 RAG experiment 설정과
Silver → Gold 데이터 가공 설정을 논리적으로 분리하는 것이다.


==================================================
10. LangChain Document 생성
==================================================

Gold의 한 artifact record를
LangChain Document로 변환한다.

Document(
    page_content="...",
    metadata={...}
)

Gold JSON 자체를 그대로 JSON dump해서 page_content로 넣지 않는다.

Embedding과 LLM이 의미를 이해하기 쉬운 텍스트로 변환한다.

예:

유물명: ...
시대: ...
재질: ...
설명: ...
관련 정보: ...

실제 field를 조사한 후 구성한다.

None,
빈 문자열,
빈 list 등의 값은 page_content에서 제외한다.

metadata에는 최소한 artifact identifier를 유지한다.


==================================================
11. Chunking
==================================================

Chunking 구현은 교체 가능한 구조로 만든다.

최소 지원:

- none
- recursive
- sentence_based
- field_based

공통 interface를 사용한다.

예:

chunk_documents(
    documents,
    config
) -> list[Document]

새로운 chunking 방식을 추가하더라도
Vector DB / Retriever / Evaluation 코드를 수정할 필요가 없게 한다.

모든 chunk에는:

- artifact identifier
- chunk_index
- chunk_type

metadata를 유지한다.


==================================================
12. Recursive Chunking
==================================================

RecursiveCharacterTextSplitter 사용.

YAML:

chunking:
  strategy: "recursive"
  chunk_size: 800
  chunk_overlap: 120

chunk_size와 overlap의 단위가
현재 구현상 character인지 token인지
문서에 명확하게 기록한다.


==================================================
13. Sentence-based Chunking
==================================================

문장 경계를 유지하는 방식으로 구현한다.

한국어 문장을 고려한다.

가능하면 불필요한 dependency 없이 구현하되,
추가 library가 필요한 경우 이유를 설명한다.


==================================================
14. Field-based Chunking
==================================================

현재 Gold가 구조화된 JSON이라는 점을 활용한다.

의미상 관련된 field들을 묶어서 chunk를 생성한다.

예:

기본 정보
설명 정보
관계 정보

단 실제 group은
Gold schema와 var_list.md를 확인해서 결정한다.

가짜 field 이름을 추측해서 구현하지 않는다.


==================================================
15. Embedding
==================================================

기본 모델:

BAAI/bge-m3

langchain_huggingface.HuggingFaceEmbeddings 사용.

YAML에서 변경 가능:

embedding:
  model_name:
  device:
  normalize_embeddings:
  query_prefix:
  document_prefix:

device=auto이면:

CUDA 가능 → CUDA
불가능 → CPU

Embedding model은 한 번만 load해서 재사용한다.

추후 다음 모델도 실험할 수 있어야 한다.

BAAI/bge-m3
intfloat/multilingual-e5-base
intfloat/multilingual-e5-large

E5처럼 query/document prefix가 필요한 모델을 위해

query_prefix
document_prefix

설정을 실제 embedding 과정에 반영한다.


==================================================
16. Chroma Vector DB
==================================================

langchain_chroma.Chroma 사용.

각 실험은 독립적인 DB 사용.

ai/rag/storage/experiments/{experiment_name}/chroma/

예:

ai/rag/storage/experiments/
├── recursive_500_overlap50_bge_m3/
├── recursive_800_overlap120_bge_m3/
├── no_chunk_bge_m3/
└── field_based_bge_m3/

Chunking 또는 embedding이 달라지면
Vector DB를 새로 구축한다.

다른 embedding 모델에서 생성한 vector를
절대 동일 collection에 섞지 않는다.

17. Retriever
==================================================

최소 다음 지원:

similarity
mmr

YAML:

retriever:
  search_type: "similarity"
  k: 5
  fetch_k: 20
  lambda_mult: 0.5

Retriever는 Ollama 없이 독립적으로 테스트 가능해야 한다.

18. Retrieval Evaluation
==================================================

evaluation dataset 형식:

[
  {
    "query": "...",
    "relevant_ids": ["..."]
  }
]

최소 metric:

Recall@1
Recall@3
Recall@5
MRR

실제 정답 데이터를 임의로 생성하지 않는다.

정답 evaluation dataset이 없다면
template/example만 만든다.

19. 실험 YAML
==================================================

예:

ai/llm/configs/experiments/exp01_recursive_500.yaml

experiment:

nested dictionary가 통째로 사라지면 안 된다.

20. 단일 실험 실행
==================================================

uv run python ai/llm/evaluation/run_experiment.py \
  --config ai/llm/configs/experiments/exp01_recursive_500.yaml

→ Document 생성
→ Chunking
→ Embedding
→ 실험별 Chroma 구축

→ 결과 저장


중요:

여기에서는 Silver 데이터를 읽지 않는다.

Silver는 build_gold_dataset 단계에서만 사용한다.

27. Gold와 실험의 관계를 문서에서 강조

Gold 고정
    ↓
chunk_size만 변경
    ↓
성능 비교

그래야 성능 차이가
Gold 데이터 변화 때문이 아니라
chunking 설정 때문이라고 해석할 수 있다.

Embedding 비교도 동일하다.

Gold 고정
Chunking 가능하면 고정
Embedding model만 변경

Retriever 비교도 동일하다.

Gold 고정
Chunking 고정
Embedding 고정
Retriever 설정만 변경
