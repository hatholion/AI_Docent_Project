# Vision 모델 학습 방식 결정 기록

EfficientNet-B0 기반 유물 분류 모델을 최종적으로 어떤 방식(head-only vs fine-tune)으로
학습시켜 배포할지 검증한 과정과 근거를 정리한다. 코드 변경 이력은 git log를 보면 되지만,
"왜 이 방식을 택했는지"는 커밋 메시지만으로는 드러나지 않아서 별도로 남긴다.

## 배경: 왜 이 검증이 필요했나

- `data/raw/real`의 클래스별 이미지 수가 3~21장으로 매우 적다 (`data/raw/synthetic`은 클래스당 약 200장).
- 기존 방식은 real 이미지를 고정 비율로 val/test에 절반씩 나눴는데, 클래스당 표본이 1~2장까지
  내려가는 경우(`ssu001846` 등) 단일 split 결과만으로는 "우연히 쉬운 조합을 뽑은 것"인지
  "실제로 잘 되는 것"인지 구분할 수 없었다.
- 이를 해결하기 위해 `split_data.py`를 stratified k-fold(3-fold) 방식으로 바꿔서, real 이미지가
  fold마다 회전하며 test로 쓰이도록 했다. 3개 fold를 합치면 보유한 real 이미지 66장 전부가
  정확히 한 번씩 test로 쓰인다.

## 학습 파이프라인 구조

fold마다 완전히 독립적으로 처음부터 학습한다 (가중치 공유 없음).

1. `train.py` — ImageNet 사전학습 EfficientNet-B0의 backbone을 고정(freeze)하고,
   분류 head(마지막 Linear)만 synthetic train 데이터로 학습 ("head-only" 체크포인트).
2. `finetune.py` — 1번 체크포인트를 이어받아 backbone 마지막 2개 feature block까지
   unfreeze해서 추가 학습 ("fine-tune" 체크포인트).
3. `evaluate.py` — 두 체크포인트 각각을 그 fold의 test 데이터로 평가.

**중요한 구조적 사실**: 1번과 2번 모두 실제로 역전파(gradient update)는 synthetic 이미지로만
일어난다. real 이미지(val)는 체크포인트 선택(`best_val_loss` 기준)과 최종 평가에만 쓰이고,
가중치 업데이트에는 한 번도 관여하지 않는다. 즉 fine-tune 단계도 "real 도메인으로 재조정"하는
게 아니라 "synthetic 도메인 안에서 더 깊은 층까지 재조정"하는 것이다. head-only vs fine-tune을
비교할 때 이 전제를 놓치면 안 된다.

## 결과 1: 3-fold 정확도

| fold | test 표본 수 | accuracy | macro_f1 | 오분류 |
|---|---|---|---|---|
| 0 | 25 | 1.0 | 1.0 | 0 |
| 1 | 21 | 1.0 | 1.0 | 0 |
| 2 | 20 | 1.0 | 1.0 | 0 |

클래스 7개 전부, 3개 fold 전부에서 precision/recall/f1 = 1.0. real 이미지 66장 전부에
대해 (각 fold에서 한 번씩) 정확히 예측했다.

## 결과 2: head-only vs fine-tune 비교

같은 fold, 같은 test 이미지 기준으로 head-only 체크포인트(`classifier_fold_*`)와
fine-tune 체크포인트(`finetune_fold_*`)를 각각 평가했다.

### 정확도 — 동률

| fold | head-only | fine-tune |
|---|---|---|
| 0 | 1.0 | 1.0 |
| 1 | 1.0 | 1.0 |
| 2 | 1.0 | 1.0 |

정확도만으로는 두 방식을 구분할 수 없었다 (천장 효과: 문제가 쉬워서 두 방식 다 만점).

### Confidence — head-only가 근소하게 우위

정답을 맞힌 샘플들의 평균 confidence:

| fold | head-only | fine-tune |
|---|---|---|
| 0 | 0.890 | 0.850 |
| 1 | 0.914 | 0.889 |
| 2 | 0.895 | 0.867 |

3개 fold 전부 head-only의 평균 confidence가 더 높았다. "fine-tune이 더 확신 있게 맞출
것"이라는 예상과는 반대 방향이었다.

### 가장 애매했던 이미지가 두 모델 간에 일치

| fold | 가장 confidence 낮은 이미지 | head-only | fine-tune |
|---|---|---|---|
| 0 | `ssu022891_real_006/007.jpg` | 0.41 / 0.52 | 0.56 / 0.60 |
| 1 | `ssu022891_real_004.png` | 0.41 | 0.54 |
| 2 | `duk000798_real_002.jpg` | 0.31 | 0.29 |

두 모델이 어려워하는 이미지가 동일하다는 건, fine-tune이 head-only와 다른 종류의 일반화
능력을 얻지 못했다는 뜻이다. 오히려 두 모델이 비슷한 특징에 의존하고 있고, 남은 어려움은
학습 방식의 차이가 아니라 **해당 real 사진 자체의 촬영 조건(조명/각도)** 에서 온다는
쪽으로 해석된다.

## 학습 곡선에서 관찰된 부가 현상

`finetune_fold_0`, `finetune_fold_2`의 학습 곡선(`runs/vision/finetune_fold_*/loss_curve.png`)에서
backbone unfreeze 직후(epoch 3~4) val accuracy가 일시적으로 급락했다가 곧 회복하는 패턴이
공통으로 나타났다. val 표본이 fold당 41~46장뿐이라 이미지 몇 장의 예측 변화만으로도 정확도가
크게 흔들리는 것으로 보이며, 체크포인트 선택 기준이 accuracy가 아니라 `val_loss`라서 이 급락이
최종 채택 체크포인트에는 영향을 주지 않았다.

## 결과 3: Head-Only Final 모델 (real+synthetic 전체 학습)

3-fold 검증은 real 이미지 일부를 의도적으로 학습에서 제외한 상태였다. 검증이 끝난 뒤에는
데이터를 더 이상 아낄 이유가 없으므로, `split_data.py --final` 모드로 real 66장 전부 +
synthetic 전체를 train에 합치고, 클래스당 1장만 sanity-check용으로 val/test에 남겨
(`data/processed/final`) head-only 방식으로 최종 모델(`runs/vision/classifier_final`)을
다시 학습했다.

- 5 epoch, 급락 없이 매끄럽게 수렴 (fold 실험에서 본 패턴과 일치)
- sanity-check 7장(클래스당 1장) 전부 정답, accuracy 1.0

이 시점에는 이 체크포인트를 배포용으로 잠정 채택했으나, 결과 6에서 `finetune_final`로
최종 변경됐다(아래 "결론 및 최종 선택" 참고). fold 체크포인트(`classifier_fold_*`,
`finetune_fold_*`)는 검증 기록으로만 남기고 배포에는 쓰지 않는다.

## 결과 4: 실제 촬영 조건 스모크 테스트 (웹캠으로 화면 재촬영)

`data/raw/real`의 사진들은 실제로는 박물관 아카이브/도록에서 모은 스튜디오 촬영 사진에
가깝다 (배경이 단색이고 조명이 균일하며, 클래스 안에서도 109×400부터 3024×3911까지
해상도가 제각각이라 웹에서 수집된 것으로 보인다). 이는 지금까지의 3-fold 검증이
"synthetic 렌더링 vs 스튜디오/아카이브 사진" 사이의 검증이었지, 실제 서비스 조건(웹캠으로
유물 또는 화면에 띄운 사진을 촬영)과는 다르다는 뜻이다.

이 갭을 확인하기 위해, `data/raw/real`의 사진 7장(클래스당 1장)을 화면에 띄워놓고 웹캠/폰
카메라로 재촬영해서 `data/webcam_test/`에 저장한 뒤 `classifier_final` 체크포인트로
예측해봤다. 화면 반사 글레어, 색조 왜곡, 기울어진 촬영 각도가 실제로 포함된 사진들이었다.

| 유물 | 정답 여부 | confidence | 비고 |
|---|---|---|---|
| bon002789 (금동 반가사유상) | ✅ | 0.978 | |
| duk000798 (청동촛대) | ✅ | 0.980 | |
| jub000702 (백자 달항아리) | ✅ | 0.983 | |
| ssu001794 (농경문 청동기) | ✅ | 0.994 | |
| ssu001846 (방패형 동기) | ✅ | 0.938 | 화면 반사 글레어 있음 |
| ssu003094 (요령식 동검) | ✅ | 0.605 | 글레어가 유물에 직접 걸침 + 가장 비스듬한 각도, 2등 후보가 0.216까지 근접 |
| ssu022891 (빗살무늬토기) | ✅ | 0.994 | |

7/7 정답. 다만 `ssu003094`는 confidence가 눈에 띄게 낮아서(0.605, 2등과 격차 작음),
글레어가 유물 위에 직접 겹치는 조건에서는 판단이 흔들릴 수 있는 경계선 사례로 보인다.

**해석**: 표본이 7장뿐이라 확정적인 결론은 아니지만, 우려했던 "스튜디오 사진으로만
검증해서 실전에 매우 약할 것"이라는 최악의 시나리오는 확인되지 않았다. 동시에
`ssu003094` 같은 사례는 글레어/반사에 약한 지점이 실제로 존재한다는 것도 보여준다.

## 결과 5: 웹캠 테스트 확장 (조건 분리) — 첫 오분류 발견

`ssu003094`의 confidence 저하가 글레어 때문인지 촬영 각도 때문인지 분리하기 위해,
`bon002789`를 중심으로 조건(글레어 유무 × 각도)을 나눠 촬영을 추가하고, 나머지 클래스도
글레어가 있는 조건으로 몇 장씩 더 촬영했다. 총 29장으로 확장.

| 유물 | 결과 (정답/전체) | confidence 범위 |
|---|---|---|
| bon002789 | **2/4** (오분류 2건) | 0.68 ~ 0.98 |
| duk000798 | 4/4 | 0.76 ~ 0.98 |
| jub000702 | 4/4 | 0.93 ~ 0.98 |
| ssu001794 | 4/4 | 0.68 ~ 0.99 |
| ssu001846 | 4/4 | 0.67 ~ 0.94 |
| ssu003094 | 5/5 | 0.61 ~ 0.96 |
| ssu022891 | 4/4 | 0.93 ~ 0.99 |

**전체 정확도 27/29 (93.1%)** — 처음으로 실제 오분류가 나왔다. 오분류 2건 전부
`bon002789`(금동 반가사유상) → `ssu001794`(농경문 청동기)로 잘못 예측됐다.

사진을 직접 비교한 결과:

- `bon002789_002` (글레어 있음, 각도는 거의 정면) → **오분류**
- `bon002789_003` (글레어 심함 + 극단적으로 기울어짐 + 색조 왜곡) → **오분류**
- `bon002789_004` (글레어 없음, 각도만 있음) → **정답** (0.75)
- `duk000798_003` (글레어 있음, 하지만 정답) → **정답** (0.76)

즉 "글레어가 있으면 무조건 틀린다"가 아니라, **`bon002789`가 글레어 조건에서 유독
취약**하다. `duk000798`(가늘고 긴 촛대 실루엣)처럼 형태가 독특한 클래스는 글레어가
있어도 안 흔들렸다. 오분류가 항상 `ssu001794`로 향한 것도 우연이 아닌 것으로
보인다 — 둘 다 청동 재질에 비슷한 녹청색 표면을 가지고 있어서, 글레어가 얼굴/옷주름
같은 세부 형태를 지워버리면 "청동색 덩어리"라는 공통된 저수준 특징만 남아 서로
헷갈리는 것으로 해석된다.

**결론**: 글레어는 클래스 전반의 confidence를 낮추지만(0.98→0.7~0.8대), 오분류까지
이어지는 건 **재질/색이 비슷하고 세부 디테일로만 구분되는 클래스 쌍**
(`bon002789` ↔ `ssu001794`)에 한정된 것으로 보인다. 이는 다음 단계인 augmentation
설계에 구체적인 방향을 제시한다 — 무작정 모든 클래스에 글레어 augmentation을 추가하기보다,
이런 취약 클래스 쌍의 구분력을 강화하는 데 초점을 맞출 필요가 있다.

## 글레어 대응 방안

비용이 낮은 순서대로 검토한다.

1. **추론 전처리로 글레어 억제 (재학습 불필요) — 시도했으나 실패**. 명도가 매우 높고
   채도가 매우 낮은 영역을 HSV로 탐지해 블러로 대체(간이 inpainting)하는 방식을
   `ai/vision/test_with_glare_suppression.py`로 구현해 `bon002789_002/003`에 적용했다.

   | 이미지 | 전처리 전 | 전처리 후 |
   |---|---|---|
   | `bon002789_002` | ssu001794(0.682) ❌ | ssu001794(0.474) ❌ |
   | `bon002789_003` | ssu001794(0.732) ❌ | ssu001794(0.825) ❌ (더 나빠짐) |
   | `bon002789_001` (정상) | bon002789(0.978) ✅ | bon002789(0.975) ✅ |
   | `bon002789_004` (정상) | bon002789(0.754) ✅ | bon002789(0.692) ✅ (소폭 하락) |

   오분류 2건 중 하나도 고치지 못했고, 정상 이미지의 confidence만 깎았다. 원인으로
   추정되는 것은 `bon002789_003`처럼 **전역적인 색조 왜곡**(주황빛 색조)이 낀 경우,
   국소적으로 "새하얗고 채도 없는" 픽셀만 잡는 마스크로는 전혀 대응이 안 된다는 점이다.
   즉 문제가 국소적 글레어 픽셀이 아니라 이미지 전체의 색/명암 분포 변화였을 가능성이
   높다. 이 방식은 폐기하고 2번으로 넘어간다.
2. **synthetic train에 글레어 시뮬레이션 augmentation 추가 (head-only) — 역시 실패**.
   [data.py](../ai/vision/data.py)의 `RandomGlare` transform(화면 반사처럼 밝고 반투명한
   사각 패치를 `p=0.2` 확률로 합성)을 train transform에 추가하고, head-only로 재학습한
   `classifier_final_glare`를 웹캠 29장으로 재검증했다.

   | 이미지 | augmentation 전 (`classifier_final`) | augmentation 후 (`classifier_final_glare`) |
   |---|---|---|
   | `bon002789_001` (정상) | bon002789(0.978) ✅ | bon002789(0.977) ✅ |
   | `bon002789_002` (글레어) | ssu001794(0.682) ❌ | ssu001794(0.672) ❌ |
   | `bon002789_003` (글레어+각도) | ssu001794(0.732) ❌ | ssu001794(0.687) ❌ |
   | `bon002789_004` (각도만) | bon002789(0.754) ✅ | bon002789(0.771) ✅ |

   전체 정확도 27/29로 동일, 오분류 2건이 그대로 남았다(오답 confidence만 미세하게
   하락, 유의미한 개선 아님). 나머지 27장도 confidence가 오르내리는 정도일 뿐
   뚜렷한 개선/악화는 없었다.

   **원인 추정**: head-only는 backbone(특징 추출기)이 완전히 고정된 상태라, train
   데이터에 글레어를 아무리 섞어도 "고정된 특징 공간 위에서 분류 경계선만 재조정"할
   뿐 특징 추출기 자체는 전혀 학습되지 않는다. 얼어있는 ImageNet backbone이 애초에
   "글레어 낀 `bon002789`"와 "깨끗한 `ssu001794`"를 비슷한 특징 벡터로 뽑아낸다면,
   그 위에 어떤 분류 경계선을 그어도 구분할 수 없다. 즉 이번 실패는 augmentation
   자체의 실패라기보다 **head-only 구조의 구조적 한계**로 보인다. 이 가설이 맞다면,
   backbone까지 역전파가 도달하는 fine-tune 단계에서 같은 augmentation을 적용해야
   특징 추출기 자체가 글레어에 강건해질 기회가 생긴다.
3. **장기: 취약 클래스 쌍(`bon002789`/`ssu001794`) 대상 데이터 보강** — 이 두 클래스는
   재질/색이 비슷해서 세부 디테일이 지워지면 구분이 어려워진다. 여유가 되면 이 두
   클래스만이라도 글레어/저조도 조건의 real 사진을 몇 장 더 확보해서 fold 검증에
   추가하는 것이 근본적인 해결책이다.

우선순위는 1 → 2 → 3 순. 1번으로 충분하면 모델을 건드리지 않고 끝낼 수 있어 가장
안전하고, 부족하면 2번(재학습, 비용 낮음)으로 넘어가고, 그래도 안 되면 3번(데이터
보강, 비용 높음)을 고려한다.

## 결과 6: fine-tune 재검토 — head-only vs fine-tune 결론을 뒤집는 발견

2번 실험(augmentation) 도중, 비교 대상으로 `finetune_final`(real+synthetic 전체로
fine-tune, augmentation 없음)과 `finetune_final_glare`(fine-tune + augmentation)도
같은 웹캠 29장으로 검증했다. 결과 4에서 사용한 4개 체크포인트 전체 비교:

| 모델 | 정확도(29장) | 오분류 |
|---|---|---|
| `classifier_final` (head-only) | 27/29 | `bon002789_002`, `bon002789_003` |
| `classifier_final_glare` (head-only + aug) | 27/29 | 동일 |
| **`finetune_final` (fine-tune, aug 없음)** | **28/29** | `ssu001846_004`만 |
| `finetune_final_glare` (fine-tune + aug) | 26/29 | `bon002789_002/003` + `ssu001846_004` |

**놀라운 점 1**: fine-tune이 augmentation 없이도 `bon002789_002/003`의 글레어 오분류를
저절로 고쳤다(0.682→0.804, 0.732→0.557). 3-fold 검증(결과 2)에서는 head-only와
fine-tune이 완전 동률이라 "fine-tune 불필요"로 결론 냈는데, 그건 **fold 검증에 쓰인
real 사진이 전부 스튜디오 품질이라 두 방식의 일반화 차이를 구분할 능력 자체가
없었기 때문**으로 보인다. 실제로 어려운(글레어) 이미지가 들어오자 차이가 드러났다.

**놀라운 점 2**: 글레어 augmentation을 fine-tune에 추가했더니 오히려 나빠졌다
(글레어 오분류가 다시 나타남). `RandomGlare`(밝은 사각 패치 합성)가 실제 글레어를
정교하게 재현하지 못해서, backbone이 실제로 학습되는 fine-tune 단계에서 그 악영향이
고스란히 반영된 것으로 보인다. **이 augmentation은 폐기했다** (`data.py`에서 제거).

**놀라운 점 3**: fine-tune 계열(augmentation 유무 무관)은 새로운 오분류
`ssu001846_004`를 만들어냈다. 사진을 확인해보니 글레어가 아니라 **초점이 심하게
나간 블러** 사진이었다 — head-only에서는 멀쩡했던 케이스다. 즉 fine-tune은
"글레어에는 더 강해지고 블러에는 더 약해지는" 트레이드오프를 보였다.

**결론**: 두더지 잡기 패턴(글레어는 고치고 블러는 새로 생김)이라 완벽한 승리는 아니지만,
같은 29장 테스트에서 `finetune_final`이 `classifier_final`을 모든 지표에서 같거나
앞선다(28/29 > 27/29, 오분류 1건 < 2건). 두 체크포인트는 동일한 EfficientNet-B0
아키텍처라 추론 속도/모델 크기 차이도 없다. "표본이 적으니 신중해야 한다"는 원칙은
1장짜리 관찰로 원인을 추측할 때 적용할 것이지, 이미 두 모델을 똑같은 조건에서 비교한
결과까지 무시하고 기존 선택을 관성적으로 유지할 근거는 아니다.

1. 글레어 시뮬레이션 augmentation은 어떤 조합에서도 순이익이 없었다 — 폐기.
2. **최종 배포 모델을 `classifier_final`(head-only)에서 `finetune_final`(fine-tune)로
   변경한다.** 기존 3-fold 검증의 "동률"은 스튜디오 사진만 써서 두 방식을 구분할
   통계적 힘이 없었던 결과였음이 드러났고, 실제 조건(웹캠)에서는 fine-tune이 낫다.
3. 새로 발견된 블러 취약점(`ssu001846_004`)은 글레어와 마찬가지로 추적이 필요한
   알려진 한계로 남긴다.

## 결론 및 최종 선택: fine-tune (`finetune_final`)

- 3-fold 검증(스튜디오 사진, 결과 2): head-only와 fine-tune 동률
- 웹캠 실전 조건(결과 4~6): fine-tune이 head-only보다 우세 (28/29 vs 27/29)
- 3-fold에서의 "동률"은 검증 방법(스튜디오 사진만 사용)의 한계였고, 실제 판단 근거는
  실전 조건 테스트 쪽에 둬야 한다.

위 근거로 **최종 배포 모델을 `runs/vision/finetune_final/best_model.pth`로 변경**했다.
다만 이것도 웹캠 29장이라는 제한된 표본 기준이며, 블러 조건(`ssu001846_004`)이라는
새로운 약점이 확인된 상태다. 표본을 늘려 재검증하면서 이 결정도 계속 갱신해야 한다.

## 남은 한계

- 3-fold 검증은 "가진 real 66장 안에서의 일관성"을 확인한 것이지, 실제 방문객이 찍을 새로운
  사진에 대한 일반화를 보장하지 않는다. 게다가 결과 6에서 드러났듯, 이 검증에 쓰인 사진이
  전부 스튜디오 품질이라 head-only와 fine-tune의 실전 일반화 차이를 애초에 구분할 수
  없었다 — "동률"이라는 결론 자체가 검증 방법의 한계였다.
- real 이미지가 학습(gradient update)에 전혀 쓰이지 않는 구조라서, synthetic 렌더링과 실제
  촬영 조건의 차이(도메인 갭)가 근본적으로 해소된 것은 아니다.
- 웹캠 테스트에서 두 가지 서로 다른 약점이 확인됐다: `bon002789`↔`ssu001794`(글레어/색조
  왜곡 조건), `ssu001846`(블러 조건). fine-tune(현재 배포 모델)은 전자를 고쳤지만
  후자는 아직 미해결 상태다 — `finetune_final`의 알려진 한계로 추적한다.
- 글레어 시뮬레이션 augmentation은 시도했지만 모든 조합에서 순이익이 없어 폐기했다
  (결과 6). 휴리스틱 augmentation이 항상 도움이 되는 건 아니라는 것을 직접 확인했다.
- 다음 단계로 고려할 것: 웹캠 테스트 표본을 늘려(블러 조건 위주로) `finetune_final`의
  블러 취약점이 재현되는지 확인, 블러 대응 augmentation(모션 블러 시뮬레이션) 시도,
  혹은 오분류가 실제로 반복되면 TTA(Test-Time Augmentation) 적용.
